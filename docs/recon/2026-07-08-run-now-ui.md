## Q1 — Existing on-demand-run affordance (OBSERVED — #224 corrected)

**#224's "no Run Now control at all (grep empty)" is false.** There is a substantial Run-now surface:

- **Check-detail "Run now" button** — `src/app/checks/[id]/page.tsx:424-431`:
  ```
  {canWrite && check.enabled && (
    <button onClick={handleRunNow} disabled={running || expectRun || latestRunStatus === "running"}
      className="sw-btn" data-testid="run-now">
      {latestRunStatus === "running" ? "Running…" : running || expectRun ? "Starting…" : "Run now"}
    </button>
  )}
  ```
  `handleRunNow` (`:350`) calls `runCheckNow(check.id)` (`:354`) and flips on a **scoped fast poll**
  (`setExpectRun(true)` → `useCheck(id, { expectRun })`, `:277-288`) so the run is caught live running→done.
- **"Run all" fan-out on Monitors** — `src/components/run-all.tsx` fires `runCheckNow` across the filtered set
  with a concurrency cap + live aggregate progress (`run-all.tsx:16,111`), used at `monitors/page.tsx:16`.
- **The mutation** — `runCheckNow` (`src/lib/api-client.ts:1508-1513`): `POST /checks/${id}/run`, no body, no
  query.

**Falsifier for #224's grep:** `grep -rniE "run.?now|runCheckNow|checks/.*/run" src/` returns the button, the
handler, `run-all.tsx`, and the api-client mutation — not empty. The likely miss: #224 grepped a narrow term
(e.g. only `RunNow` PascalCase) — the code uses `handleRunNow`, `runCheckNow`, and `data-testid="run-now"`.

## Q2 — The two gaps, and what "see the result" actually needs

### Gap A — the button is gated on `enabled`, so PAUSED monitors have no way to run (OBSERVED)
`checks/[id]/page.tsx:423`: `{canWrite && check.enabled && (…button…)}`. A paused (`enabled=false`) monitor
renders **no Run-now button**. This is exactly the S-arc sandbox case: today a user can't validate a paused
monitor from the UI at all.

### Gap B — `runCheckNow` has no sandbox param (OBSERVED)
`api-client.ts:1508`: `runCheckNow(id)` → `POST /checks/${id}/run` with no query. The API's sandbox flag is a
**query param** — `POST /checks/{id}/run?sandbox=true` (synthwatch-api `a24898d`,
`ChecksRunFunctions.cs`): `var sandbox = req.Query["sandbox"] == "true"; … if (!check.Enabled && !sandbox)
return 409`. So a normal call on a paused check is a **409** ("Monitor is paused — resume it before running");
only `?sandbox=true` runs it out-of-band. `runCheckNow` must gain an optional `{ sandbox }` → append the query.

### ★ The real scope question — "see the validation result": ALREADY BUILT (OBSERVED + INFERRED)
A button that fires into the void isn't the ask; Craig wants to SEE the result + trace. That view exists:
- The API sandbox run writes a **visible runs row + trace**, only SKIPPING `evaluate()` (no
  incident/alert/SLO side-effects) and never flipping `enabled` (`a24898d` commit body + `RunRequest.cs`
  doc-comment). So a sandbox run is a normal, visible run on the read path.
- The check-detail page already surfaces exactly that, live: the **scoped fast poll** (`useCheck(expectRun)`,
  `:279`), the **run-history list** (`RunHistory`, `:12`), the **live step checklist** (`LiveStepsChecklist`,
  `:13`), and the **trace viewer** (`TraceViewer`, `:14`). The poll keys on `recent_runs[0].status` going
  running→done, so it catches the sandbox run and auto-expands its row + trace — the same mechanism a normal
  Run-now uses today.

**→ INFERRED (strong):** firing a sandbox run on the detail page and reusing the existing poll surfaces the
validation result + trace with **no new result/progress view**. The fire button + the sandbox param are the
whole functional build. Caveat below.

### The one display nuance (optional, needs an API read-path add)
The result row will render as a **normal run** — the dashboard has no way to LABEL it "sandbox / validation
(didn't alert, didn't count, didn't resume)". The sandbox flag lives on `run_requests` (`a24898d`), not
(this PR) on the runs read DTO. So *marking the result visually as a sandbox run* would need the runs DTO to
carry the flag — a small API read-path addition, NOT required for "see the result", but nice for honesty (so
a green sandbox result isn't misread as a real passing run). Flag as an optional follow-up.

## Q3 — Auth in the browser (OBSERVED — already solved)

Mutations are already authed; no new work. `src/lib/auth.ts`: a bearer **session** minted by
`POST /api/auth/verify` is held in `localStorage` (`STORAGE_KEY = "synthwatch.session"`, `:29`) and exposed to
the api-client `request()` seam, which attaches it as `Authorization: Bearer <token>` (`:6-7`). `useAuth()`
→ `canWrite` (editor/admin) gates the UI (`checks/[id]/page.tsx:277`). Run-now, Pause, and Edit all mutate
through this path today; 401/403 are handled globally by the interceptor. The sandbox POST needs the same
editor/admin bearer — unchanged (`a24898d`: "Auth: unchanged — a mutating POST already requires the
editor/admin verb-gate").

## Scoped minimal build (do NOT build)

1. **`api-client.ts` — sandbox param.** `runCheckNow(id, opts?: { sandbox?: boolean })` → append
   `?sandbox=true` when set. One-line change; mirror the existing no-body POST.
2. **`checks/[id]/page.tsx` — show the button for paused monitors, sandbox-aware.**
   - ENABLED monitor: unchanged — normal `runCheckNow(id)`, "Run now".
   - PAUSED monitor (`!check.enabled`): render the button (drop the `&& check.enabled` gate, keep `canWrite`),
     call `runCheckNow(id, { sandbox: true })`, and **communicate it's a sandbox validation run** — distinct
     label (e.g. "Sandbox run" / "Validate (paused)") + a caption/tooltip: *won't alert, won't count toward
     SLO, won't resume the monitor*. This is the honest-render requirement (a sandbox run must not read as a
     resume).
   - Reuse the existing `setExpectRun` fast poll + `RunHistory`/`LiveStepsChecklist`/`TraceViewer` as-is to
     show the live result + trace.
3. **(Optional, gated on an API read-path add)** label the resulting run row/badge as "sandbox" once the runs
   DTO carries the flag — so a sandbox pass isn't misread as a real pass.
4. **Out of scope:** "Run all" sandbox fan-out (it iterates enabled checks; the ask is single-check paused
   validation). Could pass `sandbox` later, but not part of the minimal build.

## Dependencies / flags

- **The dashboard change is client-only and small** (a param + un-gating the button for paused + a
  sandbox-labeled variant). "See the result" reuses the existing live view — **no run-progress view to
  build.**
- **The feature is gated on the API + runner shipping**, per `a24898d`: the API `?sandbox=true` endpoint AND
  runner **migration 0064** (`run_requests.sandbox` column) must be deployed before a sandbox POST executes
  end-to-end ("Migration 0064 MUST be applied to prod BEFORE this PR deploys"). The dashboard build can land
  independently, but the button will 409 (paused) / no-op until the api+runner deploy — worth sequencing.
- **Verify on build:** confirm the fast poll activates and catches the sandbox run for a *paused* check
  (today `setExpectRun` is only reachable via the enabled-gated button; the paused path is new). INFERRED it
  works (same `recent_runs[0].status` signal), but it's the one thing to exercise end-to-end.
